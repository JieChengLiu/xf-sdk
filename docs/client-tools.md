# 客户端工具定义规范

> 使用 SDK 时，`tools_list` 上报、`tool_call` 解析和 `tool_event` 回包都由 SDK 自动完成：你只需要用 `ClientTool` 声明工具、在 handler 里执行并调用 `reply.success / failure`（iOS 返回 `.success / .failure`）。
> 下文提到的 `pluginToolWaitTimeoutMs` 对应 SDK 的 `toolTimeoutMs`。本文重点是 **工具和参数怎么定义、结果怎么回**。


面向通过 `tools_list` 注册自定义工具的接入方客户端开发。

协议本身（`tools_list` / `tool_call` / `tool_event` / `ack` / 超时）见 [tools_whitelist_flow.md](tools_whitelist_flow.md)，本文不重复，只讲**工具该怎么定义**——因为线上绝大多数"工具不触发""参数不对""明明说成功了却没生效"的问题，根因都在工具定义里，改服务端解决不了。

---

## 一、服务端会做什么（2026-09 起）

模型决定调用你的工具之后、指令下发给你之前，服务端多了一道检查：

**按你在 `tools_list` 里声明的 `parameters.required`，逐个检查模型填没填。**

- **填齐了** → 照常下发 `tool_call`，跟以前一样
- **缺了必填** → **不下发**，服务端造一条结果回给模型：

```json
{
  "success": false,
  "error": "MISSING_REQUIRED_ARGUMENTS",
  "missingArguments": ["destination"],
  "hint": "调用未执行。请先向用户提问，把上面缺失的参数问清楚，再重新发起调用。"
}
```

模型收到这个只能转去问用户补全，然后重新发起调用。你这边表现为：**这一轮收不到 `tool_call`，用户会听到一句追问**。

服务端不认识任何具体工具名，只按你的声明办事。**必填怎么设，决定权完全在你。**

判断规则里 null、空串、空数组、空对象都算"没填"。

## 二、`required` 怎么设

### 判断方法

> 能不能想出一句用户真会说、且合法的话，里面没有这个参数？

想得出来，就**不该**设成必填。

### 按"执行错了能不能撤销"分两档

这是最重要的一条，两档的修法是**相反的**：

#### 可撤销的动作 → 少设必填

播歌、导航、调音量、设闹钟这类。用户说"放首周杰伦的歌"是完全合法的请求，把 `songName` 设成必填，等于逼模型编一个歌名出来。

```jsonc
// ✗ 逼模型编造
{"name": "play_music", "parameters": {
  "properties": {"artist": {...}, "songName": {...}},
  "required": ["artist", "songName"]        // 用户只说歌手就没法调了
}}

// ✓ 放开，让模型自己挑
{"name": "play_music", "parameters": {
  "properties": {
    "artist": {"type": "string", "description": "歌手名，用户没说就留空"},
    "songName": {"type": "string", "description": "歌曲名，用户没说就留空或自行挑一首该歌手的代表作"}
  },
  "required": []
}}
```

**放开之后模型会直接执行而不是追问**，体验反而更好——用户说"放首歌"就该放，不该被反问。挑错了用户说一句"换一首"就完了，成本接近零。

#### 不可撤销的动作 → 必填保留，并明确禁止代写

发消息、打电话、下单、创建会议邀请这类。执行了收不回来。

```jsonc
{"name": "send_message", "parameters": {
  "properties": {
    "contactName": {"type": "string",
      "description": "联系人姓名。必须是用户明确说出的人，不要猜测或替用户指定。"},
    "content": {"type": "string",
      "description": "消息正文。原样使用用户表达的内容，允许最小整理（补标点、去语气词），但不要替用户构思、扩写或添加他没说过的意思。用户完全没提要发什么时，不要调用本工具、改为先询问。"}
  },
  "required": ["contactName", "content"]
}}
```

### 条件必填怎么办

有些参数只在某些场景下必填。JSON Schema 顶层的 `required` 是无条件的，表达不了这种情况——**不要为了凑而把它写进顶层 `required`**，那会在不该拦的场景把功能拦死。

用 `if`/`then` 分支声明，真正的兜底放在你自己的执行逻辑里（见第四节）。

## 三、`description` 怎么写

**写"什么时候用"，不写"这是什么"。** 模型在做选择题，它需要的是判据，不是定义。

```jsonc
// ✗ "播放音乐"
// ✓ "播放音乐。用户说'放歌''听音乐''来首X'时使用；只说歌手、只说歌名、
//    或者什么都没说都可以调用，缺的部分由你合理挑选。"
```

几条经验：

- **参数的 description 要交代"不确定时怎么办"**——"用户没说就留空"比什么都不写有效得多
- **名字相近的工具要互相点名区分**（录音 vs 录像、闹钟 vs 家电定时），只描述自己不够，得说清什么时候**不该**用自己
- **别写长长的反面清单**，容易顾此失彼；写正面的触发场景更稳
- 措辞的松紧很敏感：约束写太狠会误伤正常请求（实测把"严禁扩写润色"写进 `content` 后，"跟张伟说我晚点到"这种**说全了的**请求模型也不敢调了）

---

## 四、服务端挡不住什么

**必填校验只能挡住"没填"，挡不住"乱填"。**

模型填了一个非空、格式合法但用户根本没说过的值，服务端没有任何依据判断真假——它不懂你的音乐库、通讯录、地图数据。实测例子：

```
用户："放首周杰伦的歌"
模型：play_music {"artist":"周杰伦","songName":"七里香"}    ← 编的，但无害

用户："给张伟发条消息"
模型：send_message {"contactName":"张伟",
                    "content":"你好张伟，最近怎么样？有空的话我们聊聊。"}
                                                          ← 编了一整条正文，会真发出去
```

100 轮实测里还出现过日程时间被编成执行时刻（精确到秒）的情况——用户会在"刚才"被提醒一次。

### 所以不可撤销的动作，客户端必须自己兜

三选一，按你的产品形态挑：

1. **执行前复述确认**（推荐）：拿到 `tool_call` 后先让用户确认"发给张伟：我晚点到，对吗？"。编造的值念出来通常一听就荒谬。
2. **先做但说出来 + 可打断**：适合可撤销的动作，成本最低——对的时候零打扰，错了用户一句话纠正。
3. **有屏幕的**：弹出待确认内容让用户点。

## 五、执行结果怎么回，才能让模型自己纠错

`tool_event` 的结果会进对话历史给模型看。**结果写得好，模型能自己把错的那次纠回来**；写得含糊，它只会瞎猜。

| 情况 | 建议回法 |
|---|---|
| 成功 | `success: true` + 必要的结果数据 |
| 没找到 | `success: false` + 明确说没找到什么，别只回一个 false |
| 匹配到多个 | 回候选列表，每项带**稳定 id** + 一个**适合念出来的短名** |
| 参数不对 | 说清哪个参数不对、期望什么 |

多候选那种要特别注意：**让模型回填候选 id，不要回填名称。** 同名分店、同名联系人是常态，回填名称迟早导错地方，而且错得很隐蔽。

语音场景候选最多给 2~3 个，超过就别列了，改为要求用户说得更具体——念十几个选项没有意义。

## 六、几条硬限制

- **一次会话最多 8 个自定义工具**，超出会被截断（保留前 8 个）；`tools_list_ack` 里会回 `requestedCount` 和 `count`，不一致说明被截了
- **收到 `tool_call` 必须回 `tool_event`**，默认 **2 秒**超时。超时会**断开连接**（`reason: tool_timeout`）
- 工具执行慢的话，超时时长可以在 `config` 的 `ext` 里调：`pluginToolWaitTimeoutMs`
- `function.arguments` 是 **JSON 字符串**，不是对象
- `toolCallId` 必须原样回传，用来绑定结果

## 七、上线前自查

- [ ] 每个必填参数都过了一遍"能不能想出一句没有它的合法用户话"
- [ ] 可撤销的工具没有过度必填（不会因为少说一个词就调不动）
- [ ] 不可撤销的工具，参数 description 里明确禁止了代写/猜测
- [ ] 不可撤销的工具有执行前确认，不直接执行
- [ ] `description` 写的是触发场景，不是名词解释
- [ ] 名字相近的工具互相点名做了区分
- [ ] 多候选的返回带稳定 id 和可念短名，不靠名称匹配
- [ ] 失败结果说清了原因，不是光一个 `success: false`
- [ ] 工具数量没超 8 个
- [ ] 每个 `tool_call` 都在 2 秒内回了 `tool_event`
